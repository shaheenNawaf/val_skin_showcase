A 1920 px card on a
390 px screen.

The fitter computes s = min(max(natural, 0.35), 1). On a 390 px phone that pins the card at 0.35, so the design's 9 px caption renders at 3.1 px and the 15 px price at 5.25 px. On a 1366×768 laptop it lands at 0.60 — 5.4 px. Nothing in the UI tells the user this is happening. Pick a viewport, then pick a solution.

Viewport
SOLUTION A

Keep the floor, add a zoom

The card stays a faithful 0.35× thumbnail, but every viewport gets a real zoom control: Fit, 100%, 200%, and open full size. The buyer pans by default and can pinch or use the buttons to read anything. Smallest possible change to the rendering path.

Trade-off: the first impression is still a thumbnail. A buyer who never zooms still sees 3 px text. Cheap and safe, but it does not fix the screenshot people share.
SOLUTION B

Overlay the fields that matter

The canvas scales as today. On top of it, the handful of fields a buyer actually reads — title, seller, rank, price, status, skin count — are re-rendered as crisp HTML positioned over their canvas coordinates and sized so they never fall below 12 px. Dashed outlines mark where each one came from.

Trade-off: needs a coordinate map per theme, and the overlay must be hidden during export. Most code, but the card keeps its look and becomes readable everywhere.
SOLUTION C

Raise the design's type floor

No scaling trick at all: bump the smallest sizes in the 1920×1080 design so nothing is authored below 13 px, then keep the existing fitter. At 0.35× the smallest text lands at 4.6 px instead of 3.1 px, and at 0.60× on a laptop it lands at 7.8 px instead of 5.4 px. It is a real improvement on every screen — but see the table: on a phone it is still red. This one improves the exported PNG, which is the artefact people actually post.

Trade-off: the exported 1920×1080 PNG changes, so every already-published card looks different from its listing image. Needs a re-check of every panel that has to fit a fixed number of slots. And it does not solve the phone case on its own.
SOLUTION D

Native reflow below 900 px

Below 900 px the canvas is abandoned entirely and the same data renders as a stacked native page: title and price at real size, then panels as scrollable lists of rows with 16 px names. The 1920 canvas is used only where there is room for it.

Trade-off: two rendering paths to keep in sync, and the phone layout stops being a picture of the card. The viewer already has a partial version of this below 700 px — it just leaves the phone in the 700–900 band on the canvas.

A second fidelity bug: Catalog renders differently in the editor

Viewer — correct

viewer.css:43 defines .mgrid as the 4×3 Catalog mosaic. This is what a buyer sees.

Editor — different

grid-template-columns: repeat(auto-fill, minmax(180px,1fr)) · overflow: auto · grid-template-rows: repeat(3,1fr) left over

shared.css:265 defines .mgrid as the mosaic, but editor.css:43 — loaded after it — redefines the same class as the picker's result grid. The mosaic inherits auto-fill columns and a scrolling overflow, and keeps an orphaned grid-template-rows:repeat(3,1fr). So the seller previews Catalog in a different arrangement from the one the buyer gets.

Fix: rename one of them. The mosaic should not be called .mgrid at all — .spread-mosaic costs one selector change in layouts.js, shared.css and viewer.css and removes the collision permanently.

A third: the preview is not what gets exported

What the seller sees while editing

+ Add buttons visible · slots measured with them present

What exportCard() actually captures

body.exporting hides .add — after the grid was measured
Consequence. renderSlotsM1/M2 computes cols, visRows and the overflow count from slots.clientHeight before exportCard() adds body.exporting. That class hides the + Add button sitting at the bottom of every panel, so the PNG has more room than the layout assumed — and the +N MORE chip can be pushed out of the clipped .panel. The seller sees one arrangement, the buyer gets another.

Fix: measure once with the chrome already hidden, or better — never hide .add; render it as visibility:hidden during export so layout and capture agree.

Recommendation

What I would ship first

  • • A immediately — the zoom bar is ~15 lines and removes the worst case without touching the design. It only works if the buyer zooms.
  • • C as a design pass — the only option that improves the exported PNG, which is the artefact people actually post. It still leaves phones red on its own.
  • • B is the only option where no buyer-critical field is ever below 16 px, at any viewport. Biggest win, biggest job.
  • • D last, and only if you want phones to be a first-class buyer surface — the viewer already has a partial version of it below 700 px.
  • • The honest answer for phones is B + D together: native rows on a phone, overlay fields on a laptop.

Independent of the choice above

  • • Rename .mgrid → .spread-mosaic. One selector, kills the editor/viewer mismatch.
  • • Switch export-time hiding from display:none to visibility:hidden so preview and PNG agree.
  • • Show the current scale somewhere honest, e.g. a discreet “viewing at 42% — click to zoom” affordance.
